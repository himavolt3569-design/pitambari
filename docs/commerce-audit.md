# Reference commerce audit

Read every file under reference `src/lib` except `content/copy.ts` (parent audit), every API route, every shared type, `src/proxy.ts`, all four Functions files, and both security rules files. Reference source was not modified; secrets were not opened.

## Architecture and parity

- Next.js route handlers and server actions use Firebase Admin SDK; Firestore stores products with variant subcollections, settings/content, delivery/payment methods, orders/events, partner ledger, rate limits, counters, and idempotency claims.
- Guest cart/language persist through Zustand. Nepal address normalization and province/district validation feed authoritative quote calculation. Delivery applies province, district, valley, minimum order, free-shipping thresholds, and courier availability. Money uses integer paisa.
- Orders transactionally re-read product price/stock, decrement inventory, allocate sequential branded numbers, and save customer/order snapshots plus audit event. Payment/delivery configurations are read before that transaction (despite a comment saying fees are read inside it).
- Customer orders use a 180-day opaque HttpOnly cookie; lost-cookie lookup requires order number plus normalized mobile. Tracking projection explicitly excludes internal notes, proof paths, browser keys, and payment references.
- Shared transition planner controls ten statuses, customer cancellation versus requests, delivery failures, inventory restoration, and partner-ledger guard. Paid cancellations are labelled refunded without executing a refund.
- Admin uses Firebase ID-token exchange into five-day session cookie and superAdmin claim. Proxy supplies nonce CSP and security headers. Public/manual payments work without optional Functions; gateways have no provider adapter, partner integrations are manual, notifications only log.
- Media are base64 chunks in Firestore plus optional public filesystem mirrors. Functions include HMAC webhook, daily capped cleanup, and logging order hook.
- Existing commerce tests cover customer keys, delivery zones/eligibility, lifecycle, restocking plans, and tracking projection. They do not exercise route integration, concurrency, media privacy, real Firebase rules, or webhooks.

## Defects and adaptation risks

1. **Payment screenshots fail submission and leak publicly.** `src/app/api/checkout/upload-proof/route.ts` returns `/api/media/...` or `/uploads/...`, while `src/app/api/payments/proof/route.ts` only accepts `payment-proofs/<orderId>/...`. Uploads lack ownership checks. `src/app/api/media/[id]/route.ts` is public with year-long caching; `firestore.rules` makes media documents public. `src/lib/data/admin.ts:signedProofUrl` assumes Storage paths even though upload uses Firestore. Both uploads claim success even if cloud and local storage fail.
2. **Idempotency concurrency hole.** `src/app/api/orders/route.ts` sets the key before claim, then catch unconditionally releases it. A simultaneous rejected claim deletes another request's in-flight lock. `src/lib/utils/request-guard.ts` completes the key separately from the order transaction, allowing duplicates after a post-commit error. Replays do not restore the original customer cookie. Key is not bound to payload/customer.
3. **Revocation ignored for active admin sessions.** `src/lib/auth/session.ts:getAdminUser` calls `verifySessionCookie(cookie, false)`. Disabled/revoked admins may continue using an issued cookie until expiry, contradicting the surrounding documentation.
4. **Payment races and lifecycle conflicts.** Manual proof checks payment status before a separate update; concurrent verification may be overwritten. Optional `functions/src/index.ts:paymentWebhook` allows later differently identified events to downgrade paid/refunded states and independently mutates order status outside the central planner.
5. **Refund semantics.** `src/lib/commerce/order-transition.ts` marks a paid cancellation refunded before money is actually returned. `apply-transition.ts` replaces cancellation metadata on decision, losing original requester/reason. Any linked partner ledger record blocks cancellation, including records that may already have compensating entries.
6. **Storage and rules drift.** Rules comments say server-only writes, but authenticated superAdmin clients can directly alter products/orders/payments. Variant reads are public even beneath inactive products. Storage proof creation is unauthenticated and not linked to a valid order. Newly added media chunks are denied direct reads but served publicly through Admin SDK. Avoid inheriting these assumptions.
7. **Fallback content can reactivate presentation.** `src/lib/data/storefront.ts` returns defaults for empty active product/FAQ sets, so disabling all entries can still show bundled content. Firestore read failure silently falls back, while order placement still needs a functioning database.
8. **Deployment configuration matters.** New project must have isolated Firebase credentials/project, seed, rules/indexes, custom claim setup, and domain. Rename TMG order/cookie/storage/app identifiers and branded defaults. Nominatim user-agent embeds TMG and a global Firestore rate gate; geolocation cannot work offline. Gateway boolean alone does not implement actual payment initiation.
9. **Scale/robustness limits.** Admin counts and partner reports scan whole collections; customer history scans arbitrary first 100 before sorting. Rate limits trust proxy headers and rely on platform sanitization. Cleanup removes at most 500 expired rows per collection daily. Cart quantity/remove keys only variantId, although add identity includes productId. Money multiplication and summation do not check safe integer overflow.

These are source-audit findings, not evidence of exploitation or live deployment behavior.
